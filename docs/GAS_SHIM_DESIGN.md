# GAS 범용 중계층(shim) 설계 문서

작성일: 2026-08-25
상태: **설계 검토용 초안. 아직 구현하지 않음.**
대상 코드: `src/utils/gasService.ts` (특히 `getGASCodeTemplate()`, 734행 이하)
관련 문서: `FVG_project/docs/SHIM_RULES_REVIEW.md` — 여기 정의한 규칙 4개를 자매 프로젝트에 대조한 검토 결과

이 문서는 지금의 Google Apps Script(GAS) 연동 구조를 진단하고, Code.gs를 스키마를 모르는 **얇은 중계층(shim)** 으로 바꾸는 설계안을 정리한다. 구현 여부를 판단하기 위한 근거 문서이며, 이 문서 작성 시점에 코드는 전혀 변경하지 않았다.

용어: **shim**은 소프트웨어 일반 용어로, 두 층 사이에 끼워 넣는 로직 없는 얇은 중계층을 뜻한다(`containerd-shim`, UEFI `shim`, Windows Application Compatibility Shim 등). 이 문서에서는 이후 "shim"으로 통일하되, 교사용 문서에 옮길 때는 "얇은 중계층"으로 풀어 쓰는 편이 낫다.

---

## 1. 왜 이 구조가 OAuth 없이 동작하는가

현재 구조는 다음과 같다. Node.js 서버는 없다 — `package.json`에 `express`가 들어 있으나 코드에서 한 번도 import하지 않고 `server.js`도 존재하지 않는다.

```
브라우저(React/Vite) --fetch--> GAS Web App(/exec) --SpreadsheetApp--> Google Sheets
```

브라우저가 Google API를 직접 호출하지 않는다는 것이 핵심이다. GAS 웹앱 URL(`.../exec`)은 그냥 공개 HTTPS 엔드포인트이고, `fetch()` 입장에서는 상대가 구글인지 여부가 무관한 평범한 REST API다. 그래서 access token도, 스코프도, 동의 화면도 필요 없다.

인증은 **배포 시점에 이미 끝나 있다.** `getGASCodeTemplate()`의 설치 안내 주석이 그 조건을 명시한다.

- 다음 사용자로 실행: **나(내 계정)**
- 액세스 권한: **모든 사용자(Anyone)** — 필수

교사가 Apps Script에서 [배포]를 누를 때 구글이 권한 승인 다이얼로그를 띄우고, 교사가 한 번 동의한다. 그 동의가 스크립트에 영구 저장된다. 이후 `/exec`로 들어오는 모든 요청은 익명이지만, 실행은 구글 서버 내부에서 **소유자 권한으로** 일어난다.

시트 지정조차 필요 없다. `SpreadsheetApp.getActiveSpreadsheet()`는 컨테이너 바인딩 — 스크립트가 그 시트에 물리적으로 붙어 있어 `spreadsheetId`가 코드에 아예 없다.

즉 **GAS가 자격증명을 들고 있는 프록시 서버 역할을 무료로 대신해 준다.** `drive.file` 스코프와 Picker는 "내 서버가 사용자를 대신해 구글 API를 호출"하는 전제에서 필요한 물건인데, 여기서는 그 대리 호출을 구글이 자기 인프라 안에서 처리한다.

### 1.1 이 선택이 사고 파는 것

**얻는 것**

- Google Cloud Console 의존이 0이다. OAuth 클라이언트, 동의 화면, 앱 검증 심사, Picker API 키, HTTP 리퍼러 제한, `redirect_uri` 등록이 전부 불필요하다.
- 동의 화면을 "테스트" 상태로 방치했을 때 refresh_token이 7일 만에 만료되는 함정이 없다.
- **쿼터가 교사 계정별로 분산된다.** 공용 배포 방식은 Sheets API 쿼터가 개발자의 Cloud 프로젝트 하나에 전부 몰리지만(프로젝트당 분당 300 요청), 이 구조는 그 천장이 없다.
- 개발자 서버가 구글 자격증명을 **한 번도 만지지 않는다.** 데이터가 각 교사의 드라이브에만 존재하므로 개발자가 학생 데이터의 관리자가 되지 않는다. 미성년자 데이터를 다루는 교육용 도구에서 실질적인 이점이다.

**잃는 것**

- **1시트 1배포.** 교사마다 각자 코드를 붙여넣고 각자 배포해야 한다.
- **`/exec` URL이 평문 bearer 자격증명이다.** URL을 아는 사람은 인증 없이 시트를 읽고 쓸 수 있다.
- GAS cold start 지연 1~3초.
- CORS 우회가 필요하다. POST에 `Content-Type: text/plain;charset=utf-8`을 쓰는 이유가 이것이다(`gasService.ts` 내 모든 POST). `application/json`을 쓰면 preflight OPTIONS가 발생하는데 GAS는 이를 처리하지 못한다. `/exec`가 `script.googleusercontent.com`으로 302 리다이렉트되는 구조라 simple request로 만들어 우회할 수밖에 없다.

### 1.2 자매 프로젝트와의 대조

`FVG_project`(Next.js + Vercel)는 같은 출발점(컨테이너 바인딩 GAS)에서 정반대를 선택했다.

| | sih_project (현재) | FVG_project |
|---|---|---|
| 배포 단위 | 교사 1명 = 배포 1개 | 공용 배포 1개 = 교사 N명 |
| 인증 시점 | 배포할 때 1회 | 요청마다 |
| 인증 주체 | 교사 본인 | 앱이 대행 (`drive.file` OAuth + Picker) |
| 자격증명 보관처 | 교사의 Apps Script 프로젝트 | 학생 링크 안에 AES-256-GCM 암호화 (`lib/studentToken.ts`) |
| 스키마 소유자 | 각 교사의 Code.gs (버전 분기 가능) | 서버 `lib/appData.ts` (항상 단일 버전) |
| Sheets API 쿼터 | 교사 계정별 분산 | 개발자 Cloud 프로젝트 하나에 집중 |

**핵심은 Picker의 유무가 아니라 "배포 단위를 누가 소유하는가"이다.** 공용 배포 하나로 N명을 서비스하는 순간 "이 요청이 어느 교사의 시트인가"를 앱이 알아야 하고, 그러면 앱이 구글에 인증해야 하며, 그 귀결이 OAuth + `drive.file` + Picker다. FVG의 복잡도는 잘못 고른 것이 아니라 "공용 배포 1개 + 개발자가 배포를 통제"를 사기 위해 지불한 값이다.

## 2. 현재 Code.gs가 실제로 무엇을 들고 있는가

`getGASCodeTemplate()`이 반환하는 문자열 = 642줄. 구성:

- `doGet` action 5개: `getSettings`, `getGroupPasswords`, `getTopics`, `getAllGroupData`, `getEvaluations`
- `doPost` action 7개: `saveSettings`, `saveAllGroupPasswords`, `saveGroupPassword`, `resetGroupPassword`, `saveGroupData`, `saveTopics`, `saveEvaluation`
- `ensure*` 함수 5개: 탭 생성 + 서식 + seed 데이터

### 2.1 탭 스키마 5개 (코드 실측)

| 탭 상수 | 탭 이름 | 열 수 | 헤더 |
|---|---|---|---|
| `SHEET_CONFIG_NAME` | `환경설정` | 3 | 설정 항목 (Key) / 설정값 (Value) / 설명 및 안내 |
| `SHEET_SETTINGS_NAME` | `환경설정_주제목록` | 14 | 주제ID / 탐구 주제명 / 대상 학년 / 대상 반 목록 / 모둠 목록 / 독립변인(X)명 / X단위 / 종속변인(Y)명 / Y단위 / 기본 추세선 / 과학적 개념 가이드 / 기울기 의미 가이드 / 활성화 / 탐구 결론 질문 및 서술 문항 |

### 2.2 진단: 로직 결합도 0, 스키마 결합도 100

Code.gs에 알고리즘은 없다. 회귀분석과 이상치 판정은 `src/utils/mathAnalysis.ts`, 모둠 분배는 `src/utils/distributionHelper.ts`, PDF·인쇄·QR도 모두 클라이언트에 있다. 새 화면 추가, 계산식 변경, 그래프 개편, UI 개편은 Code.gs를 건드리지 않고 `git push`로 끝난다.

그러나 **스키마는 전부 Code.gs에 박혀 있다.**

```javascript
// ensureDataSheet — 헤더 14열이 통째로 하드코딩
sheet.appendRow([
  '타임스탬프', '주제ID', '학년', '반', '모둠명', '측정차수',
  '독립변인(X)', '종속변인(Y)', '이상치여부', '측정메모',
  '문항1_답변(자료해석)', '문항2_답변(과학원리)', '문항3_답변(오차분석)', '전체_보고서_통합답변'
]);

// saveGroupData — 열 인덱스 하드코딩
if (r[1] == payload.topicId && r[2] == payload.grade &&
    r[3] == payload.classNum && r[4] == payload.groupName) { ... }
pwSheet.getRange(i + 1, 5).setValue(String(payload.groupPassword));

// getSettings — 설정 키 문자열 분기
if (key === '교사_비밀번호' || key === 'teacherPassword') { ... }
else if (key === '전체_모둠_데이터_확인_허용' || key === 'allowClassOverview') { ... }
```

따라서 재배포 트리거는 "코드 수정"이 아니라 **"스키마 변경"** 이다. 구체적으로 다음이 전부 전 교사 재배포를 요구한다.

- 설정 토글 하나 추가 → `getSettings` / `saveSettings` 수정
- 보고서 문항 3개 → 5개 → `ensureDataSheet` 헤더 + 열 인덱스 수정
- 루브릭 항목 조정 → `ensureEvaluationsSheet` 수정
- 새 데이터 탭(출석, 실험사진 등) → 새 action 추가

교육용 앱에서 "선생님이 항목 하나 추가해 달라"는 가장 흔한 요청 유형이다.

### 2.3 진짜 비용은 재배포가 아니라 버전 분기

교사 A는 구버전 Code.gs(14열), 교사 B는 신버전(16열)을 쓰는데 React는 하나뿐이고 항상 최신이다. 최신 React가 `values[i][15]`를 읽으면 A교사 시트에서는 조용히 `undefined`가 나온다. **예외도 콘솔 에러도 없이** 빈 값으로 렌더링되고 끝난다.

결국 클라이언트가 GAS 버전을 감지하고 협상하는 코드를 짜게 되는데, 이것이 실제 비용이다. `FVG_project`는 열 위치를 서버 `lib/appData.ts`가 단독으로 결정하고 서버가 항상 한 버전이므로 이 상황이 구조적으로 발생할 수 없다.

## 3. 순진한 shim이 왜 위험한가

Code.gs를 그냥 얇게 만들어 탭 이름·헤더·열 순서를 React가 요청에 실어 보내게 하면, 스키마 지식이 100% React로 이동해 `git push`만으로 스키마를 바꿀 수 있게 된다. 하지만 동시에 **스키마 권한이 서버 1곳에서 브라우저 N개로 분산된다.**

지금의 642줄 Code.gs는 뚱뚱한 대신 **시트당 단일 스키마 게이트키퍼** 역할을 하고 있다. 클라이언트가 무엇을 보내든 GAS가 자기가 아는 모양으로 강제한다. 순진한 shim은 그 방어막을 걷어낸다.

### 파손 경로 3가지

**1. 헤더 드리프트 — 조용한 열 밀림**
shim이 "탭이 없을 때만 헤더 생성"이라면, 기존 14열 탭에 React가 16열짜리 행을 append한다. 헤더는 14열 그대로이고 데이터만 16개가 되어 이후 읽기가 전부 어긋난다. 에러는 나지 않는다.

**2. 열 재정렬 — 혼합 오염**
React v2가 열 순서를 바꾸면 같은 탭에 구순서 500행과 신순서 20행이 공존한다. 이 시점부터 그 탭은 **어떤 인덱스로도 올바로 읽을 수 없다.** 복구하려면 행별로 어느 버전인지 판별해야 한다.

**3. `matchCols` 오적용 — 실제 데이터 삭제**
현재 코드가 이미 delete-then-append 패턴을 쓴다.

```javascript
// saveGroupData — 기존 모둠 행 삭제 후 재삽입
for (let i = allRows.length - 1; i >= 1; i--) {
  const r = allRows[i];
  if (r[1] == payload.topicId && r[2] == payload.grade &&
      r[3] == payload.classNum && r[4] == payload.groupName) {
    sheet.deleteRow(i + 1);
  }
}
```

범용 shim이면 이 `1,2,3,4`를 React가 보낸다. 클라이언트가 스키마 v2를 가정해 `2,3,4,5`를 보내는데 시트가 v1이면 **엉뚱한 열로 매칭해 다른 모둠 데이터를 삭제한다.** 최악은 매칭이 전부 성립해 탭 전체가 지워지는 경우다.

### 가장 나쁜 점: 재배포 없이도 발생한다

위 시나리오는 "교사가 구버전 Code.gs를 쓸 때"만의 문제가 아니다. **구버전 브라우저 탭 하나면 발생한다.**

학생이 어제 열어둔 탭(v1 번들)과 오늘 새로고침한 탭(v2 번들)이 같은 shim을 호출한다. shim은 스키마를 모르므로 둘 다 순순히 처리한다. 서비스 워커 캐시, 뒤로가기 복원, 태블릿 절전 복귀는 교실 환경에서 흔한 일이다.

## 4. 안전 규칙 4개 — 설계의 핵심

shim이 스키마를 몰라도 안전하도록 만드는 규칙이다. 넷 다 shim에 한 번만 넣으면 이후 고칠 일이 없다. 규칙 1~3은 데이터 무결성을, 규칙 4는 접근 권한을 담당한다.

### 규칙 1 — 스키마 버전 핸드셰이크

shim이 설정 탭(규칙 4 적용 후 이름은 `SIH_PUB_설정`)에 `SCHEMA_VERSION` 키를 보관하고, 모든 요청이 `schemaVersion`을 실어 보낸다.

```
client == sheet  →  통과
client <  sheet  →  거부. "페이지를 새로고침하세요" (구버전 브라우저 탭 차단)
client >  sheet  →  거부. "교사 콘솔에서 시트 업그레이드가 필요합니다"
```

shim은 스키마의 **내용**은 모르지만 **숫자 하나**는 안다. 그것만으로 게이트키퍼가 복원되고 3장의 파손 경로 3개가 전부 여기서 막힌다. 약 20줄이다.

> **이 규칙은 처음부터 넣어야 한다.** shim은 한 번 배포하면 사실상 다시 고칠 수 없다는 것이 존재 이유다. 버전 핸드셰이크를 나중에 추가하려면 전 교사 재배포가 필요해지고, 그러면 shim으로 전환한 의미 자체가 무너진다.

### 규칙 2 — 기존 탭 변형 금지, 탭 이름 버저닝

스키마가 바뀌면 `통합_실험데이터`를 고치지 않고 `통합_실험데이터_v2`를 새로 만든다. 구 탭은 손대지 않으므로 꼬일 수가 없고, 그대로 읽을 수 있으며, 마이그레이션은 교사가 명시적으로 누르는 선택 작업이 된다.

"기존 탭에 열을 추가"하는 것을 허용하는 순간 규칙 1이 있어도 사고 여지가 남는다. 아예 금지하는 편이 싸다.

실사용자가 없는 현재 시점에서는 v1으로 시작하고 규칙만 확정해 둔다.

### 규칙 3 — 삭제 금지, append-only + 최신값 우선 읽기

shim의 API에서 행 삭제와 범위 삭제를 아예 제거한다.

**얻는 것**

- 스키마가 어긋나도 기존 데이터가 물리적으로 사라질 수 없다. 최악이 "쓰레기 행 혼입"이고 이는 복구 가능하다.
- **현재 코드의 동시성 문제가 함께 해결된다.** `getDataRange()`로 전체를 읽고 루프에서 `deleteRow`하는 구조는 두 모둠이 동시에 저장하면 행 인덱스가 어긋난다. `values.append`는 구글이 다음 빈 행을 안전하게 배정한다.
- 수정 이력이 남아 "학생이 실수로 지웠다"는 상황을 복구할 수 있다.

**비용**

행이 증가하는 것뿐이며, 교실 규모(연간 수백~수천 행)에서 시트 상한(1000만 셀) 대비 무의미하다.

다만 **교사가 시트를 직접 열어볼 때 중복 행이 보인다**는 실질적 단점이 있다. 이 앱은 교사가 원본 시트를 직접 확인하는 것을 전제하므로 무시할 수 없다. 완화책으로 교사 콘솔에 명시적 "이력 정리" 버튼을 두어, 교사가 누를 때만 키별 최신 행을 남기고 과거 행을 정리하도록 한다. 자동 실행이 아니라 명시적 조작이므로 안전하다.

### 규칙 4 — 탭 이름 접두사가 접근 권한을 표현한다

범용 shim의 `getTab(name)`은 원래 **시트의 아무 탭이나** 읽는다. 교사가 그 시트에 개인 메모 탭을 추가하면 그것도 `/exec` URL만으로 읽힌다. 8장에서 다루는 두 문제(엔드포인트 노출, 교사 비밀번호 평문)가 모두 여기에서 나온다.

해법은 **탭 이름 접두사에 권한을 인코딩**하는 것이다.

| 접두사 | 교사 토큰 | 담을 내용 |
|---|---|---|
| `SIH_PUB_` | 불필요 | 주제 목록, 실험 데이터, 공개 설정 토글 |
| `SIH_TCH_` | 필수 | 모둠 비밀번호, 평가·피드백, 인증 정보 |
| 접두사 없음 | **접근 불가** | 교사 개인 탭 (자동 보호) |

shim은 **접두사 문자열 2개**만 알면 된다. 이는 스키마 지식이 아니므로 규칙 1~3과 마찬가지로 한 번 배포하면 영구히 고칠 일이 없다.

이 규칙을 도입하려면 현재 탭 이름(`환경설정`, `통합_실험데이터` 등)을 전부 바꿔야 한다. **실사용자가 없는 지금이 이름을 바꿀 수 있는 마지막 시점이다.**

현재 `환경설정` 탭은 둘로 쪼개야 한다. 학생도 `allowClassOverview` 같은 토글은 읽어야 하기 때문이다.

- `SIH_PUB_설정` — 권한 토글 3종, `SCHEMA_VERSION`
- `SIH_TCH_인증` — 교사 비밀번호, 세션 토큰, 실패 횟수

## 5. shim API 제안 — action 7개

| action | 토큰 | 역할 |
|---|---|---|
| `getMeta()` | — | `SCHEMA_VERSION`, shim 자체 버전 반환 |
| `getTab(name)` | 접두사에 따름 | 탭 전체를 2D 배열로 반환. 없으면 `null` |
| `ensureTab(spec)` | 교사 | 탭이 없을 때만 생성 — 헤더·서식·seed rows 적용. 있으면 no-op |
| `appendRows(tab, rows)` | 접두사에 따름 | 순수 추가 |
| `upsertRows(tab, matchCols, rows)` | 접두사에 따름 | `matchCols` 일치 시 제자리 갱신, 없으면 추가. **삭제 없음** |
| `verifyPassword(tab, matchCols, matchValues, secretCol, candidate)` | — | 지정 행의 비밀 값과 후보를 비교해 **불리언만** 반환. 값 자체는 절대 반환하지 않음 |
| `issueTeacherToken(candidate)` | — | 교사 비밀번호 검증 성공 시 랜덤 세션 토큰 발급(만료시각과 함께 `SIH_TCH_인증`에 저장) |

뒤 두 개는 8장에서 설명하는 비밀번호 평문 노출 문제의 해법이다. 검증 로직 자체는 "지정한 셀의 값과 후보를 비교한다"는 고정 동작이라 스키마 지식이 아니며, shim이 영구히 고칠 필요가 없다는 성질을 유지한다.

### 5.1 `ensureTab`의 spec — 서식은 담되 의미는 담지 않는다

`ensureConfigSheet`가 하는 일 중 React로 그냥 옮길 수 없는 것들이 있다. 이들은 GAS 고유 기능이라 데이터만 주고받는 API로는 표현되지 않는다.

- `setNumberFormat('@')` — 값 열을 Plain Text로 지정. **비밀번호 `0000`이 숫자 `0`으로 축약되는 것을 막는 필수 처리다.** 규칙 4 적용 후에는 비밀번호가 `SIH_TCH_인증` 탭으로 옮겨가므로 그 탭에 반드시 필요하고, 모둠 비밀번호 탭(`SIH_TCH_모둠비밀번호`)에도 같은 이유로 필요하다.
- `setFrozenRows(1)`, `setBackground(...)`, `setFontWeight('bold')`, `autoResizeColumns(...)`

이를 **일반화된 지시어**로 표현하면 shim이 각 열의 의미를 모른 채 지시만 적용할 수 있어 스키마 비의존성이 유지된다.

```
{
  tab: 'SIH_PUB_설정',
  headers: ['설정 항목 (Key)', '설정값 (Value)', '설명 및 안내'],
  columnFormats: { B: '@' },
  freezeRows: 1,
  headerBackground: '#d9ead3',
  autoResizeColumns: [1, 3],
  seedRows: [
    ['SCHEMA_VERSION', '1', '시트 스키마 버전. 임의로 수정하지 마세요.'],
    ['전체_모둠_데이터_확인_허용', 'TRUE', '...'],
    ...
  ]
}
```

이 spec 정의는 전부 React 쪽 모듈이 소유한다.

### 6.1 검증 중 발견: 파괴적 연산이 1곳이 아니라 4곳이다

계획 단계에서는 `saveGroupData` 하나만 문제로 봤으나, Code.gs 템플릿을 전수 조사한 결과 데이터를 지우는 지점이 **4곳**이다. 그중 둘은 **탭 전체를 비운다.**

| 위치 (템플릿 내 상대 행) | action | 연산 | 범위 |
|---|---|---|---|
| L360 | `resetGroupPassword` | `deleteRow(i+1)` | 해당 비밀번호 행 1개 |
| L409 | `saveGroupData` | `deleteRow(i+1)` | 해당 모둠의 기존 행 전부 |
| L290 | `saveAllGroupPasswords` | `getRange(2,1,lastRow-1,6).clearContent()` | **`환경설정_모둠비밀번호` 탭 전체** |
| L465 | `saveTopics` | `getRange(2,1,lastRow-1,14).clearContent()` | **`환경설정_주제목록` 탭 전체** |

뒤의 두 건은 shim 도입과 무관하게 **현재 코드에 존재하는 잠재적 데이터 손실 위험**이다. 두 곳 모두 페이로드가 비어 있어도 막는 가드가 없다.

```javascript
// saveTopics — payload.topics가 없거나 빈 배열이면
// 전체를 지우고 아무것도 쓰지 않는다 = 주제 정의 전량 소실
const topics = (payload && payload.topics) || [];
const lastRow = sheet.getLastRow();
if (lastRow > 1) {
  sheet.getRange(2, 1, lastRow - 1, 14).clearContent();
}
topics.forEach((t) => { ... });
```

`saveAllGroupPasswords`도 `incoming = payload.passwords || {}`로 같은 형태다. 네트워크 오류로 잘린 요청, React 상태 초기화 타이밍 버그, 구버전 탭의 빈 상태 전송 중 어느 하나만 발생해도 교사가 입력한 전체 주제 정의나 전체 모둠 비밀번호가 사라진다.

**규칙 3(append-only)은 이 4곳을 전부 무해화한다.** 반대로 shim 전환을 하지 않기로 결정하더라도, 최소한 이 두 곳에 "빈 페이로드면 거부" 가드를 넣는 것은 별도로 검토할 가치가 있다.

한편 `saveEvaluation`(#12)은 이미 삭제 없이 `appendRow`만 한다. 즉 `평가_피드백` 탭은 이미 이력이 누적되는 구조이며, append-only 방식이 이 앱에서 실제로 동작 가능하다는 선례다.

## 7. React 쪽에 새로 생기는 책임

1. **탭 스펙 모듈이 필요하다.** 탭 이름·헤더·서식·seed 데이터 정의를 한곳에 모은다. `FVG_project`의 `lib/google/template.ts` + `lib/appData.ts`가 담당하는 역할에 해당한다. 현재 `ensure*` 5개 함수의 내용이 그대로 이 모듈로 이동한다.

2. **읽기 축약 로직이 필요하다.** `fetchAllGroupsData`는 `(주제ID, 학년, 반, 모둠명, 측정차수)`를 키로 그룹핑해 타임스탬프가 가장 최신인 행만 취해야 한다. 이것이 규칙 3의 대가다.

3. **모든 요청에 `schemaVersion`을 첨부한다.** 그리고 shim이 버전 불일치로 거부했을 때의 사용자 대면 처리(새로고침 안내 / 시트 업그레이드 안내)를 UI에 추가한다.

4. **KV 파싱이 클라이언트로 이동한다.** 현재 `getSettings`가 `'전체_모둠_데이터_확인_허용'` 등 키 문자열을 GAS에서 분기하는데, 이 매핑이 React로 옮겨온다. 다만 `'0'` → `'0000'` 보정 로직은 **이동하지 않는다** — 비밀번호가 더 이상 클라이언트로 내려오지 않으므로 shim 내부의 비교 시점에서 처리한다.

5. **인증 흐름이 바뀐다.** `teacherSettings.teacherPassword`를 참조하는 곳은 실측 6곳이며 두 부류다.

   | 파일 | 행 | 성격 |
   |---|---|---|
   | `IndexSelectionScreen.tsx` | 134 | 비교 |
   | `TeacherAuthModal.tsx` | 43 | 비교 |
   | `TeacherDashboard.tsx` | 158, 296 | 비교 |
   | `TeacherDashboard.tsx` | 1711, 1811 | **평문 화면 출력** |

   비교 4곳은 `issueTeacherToken` 호출로 교체하고, 출력 2곳은 제거한다. 받은 토큰은 `sessionStorage`에 보관하고 `SIH_TCH_` 탭 요청마다 첨부한다. `TeacherSettingsConfig` 타입에서 `teacherPassword` 필드 자체가 사라지므로 타입 검사가 누락 지점을 잡아준다.

6. **모둠 비밀번호 검증도 서버 호출로 바뀐다.** 학생 입장 화면이 `getGroupPassword`로 로컬 비교하던 것을 `verifyPassword` 호출로 교체한다. 네트워크 왕복이 생기므로 입력 폼에 로딩 상태 처리가 필요하다.

## 8. 남은 한계와 완화책

3장~7장의 설계를 적용해도 GAS 프록시 구조 자체에서 오는 한계 3가지가 남는다. 각각에 대해 실제로 효과가 있는 완화책과, 효과가 없는 것으로 확인된 접근을 함께 정리한다.

### 8.1 교사 온보딩 — 사본 배포로 절반 해결

**완화책: 템플릿 시트 사본 배포.** Code.gs가 미리 붙어 있는 템플릿 스프레드시트를 만들고, 공유 URL의 `/edit`을 `/copy`로 바꾼 링크를 배포한다. 컨테이너 바인딩 스크립트는 사본에 함께 복사되므로 **642줄 복붙 단계가 사라진다.** 이 단계는 일부만 붙여넣기, 기본 `myFunction` 잔존 등 사고가 가장 많이 나는 지점이라 이득이 크다.

**그러나 배포는 복사되지 않는다.** 사본은 새 스크립트 프로젝트이므로 deployment ID가 없다. 교사가 여전히 수행해야 하는 절차:

```
확장 프로그램 > Apps Script > 배포 > 새 배포
  유형: 웹 앱
  실행: 나(내 계정)
  액세스: 모든 사용자   ← 놓치면 전부 실패
> 권한 승인 > "고급" > "안전하지 않음으로 이동" > 웹 앱 URL 복사
```

검증받지 않은 스크립트이므로 "안전하지 않은 앱" 경고 화면이 반드시 뜬다. 비전문가에게 가장 부담되는 지점이며 제거할 방법이 없다.

**버전 고착은 그대로 남는다.** 3월에 사본을 뜬 교사는 3월판 Code.gs를 계속 쓴다. 그래서 규칙 1(버전 핸드셰이크)이 여전히 필수다.

> 중앙에서 코드를 업데이트하는 방법은 Google Workspace Marketplace 부가기능으로 배포하는 것뿐인데, 여기에는 앱 검증 심사가 붙어 애초에 GAS를 선택한 이유가 무효화된다. 현재 규모에서는 과하다.

### 8.2 `/exec` 엔드포인트 노출 — 접두사 allowlist로 범위 축소

**효과 없는 접근: 스프레드시트 공유 설정 잠그기.**

`/exec` URL은 스프레드시트 URL이 아니며 시트의 공유 설정과 무관하다. "실행: 나(소유자)"의 의미가 정확히 이것이다 — 요청자는 그 시트에 **아무 권한도 필요 없다.** 시트가 완전 비공개(소유자 전용)여도 `/exec`는 읽고 쓴다. 구글 계정이 없는 학생이 앱을 쓸 수 있는 이유가 바로 이 성질이다.

즉 시트는 **이미 비공개**이고, 유출 경로는 `/exec` URL 그 자체다. 공유 설정으로 더 잠글 것이 없다.

**실효 있는 완화: 규칙 4의 탭 접두사 allowlist.** shim이 `SIH_`로 시작하지 않는 탭을 무조건 거부하면, 교사가 같은 시트에 추가한 개인 탭은 자동으로 보호된다. 범용 shim이 피해 범위를 "이 앱이 쓰는 탭"에서 "시트 전체"로 넓히는 문제가 여기서 되돌려진다.

다만 **`SIH_PUB_` 탭은 여전히 URL만으로 읽고 쓸 수 있다.** 이는 설계상 불가피하다 — 학생이 로그인 없이 실험 데이터를 읽고 써야 하는 것이 이 앱의 요구사항이기 때문이다. `/exec` 유출로 발생하는 실질적 추가 피해는 "타 학급 데이터 조작"이며, 교사 전용 데이터는 8.3의 토큰으로 분리된다.

### 8.3 교사 비밀번호 평문 노출 — 검증 이관 + 토큰

문제를 두 개로 분리해야 답이 나온다.

- **(i)** 비밀번호가 브라우저까지 내려온다
- **(ii)** 인증 판정이 클라이언트에서 일어난다

**(i) 검증을 shim으로 이관한다.**

`getSettings` 응답에서 `teacherPassword`를 제거하고 권한 토글만 내려보낸다. 대신 `verifyPassword` action이 시트의 값과 후보를 비교해 **불리언만** 반환한다. 비밀번호가 브라우저에 도달하지 않으므로 localStorage 평문 저장과 대시보드 평문 표시가 함께 사라진다.

모둠 비밀번호도 동일한 문제다. 현재 학생 화면이 `getGroupPasswords`로 **전 모둠의 비밀번호를 통째로** 받아간 뒤 클라이언트에서 비교한다. 같은 방식으로 `verifyPassword` 호출로 전환해야 한다.

**(ii) 교사 세션 토큰으로 데이터 자체를 가린다.**

(i)만 적용하면 `setIsUnlocked(true)`를 콘솔에서 강제하는 우회가 여전히 가능하다. 이를 막으려면 교사 전용 **데이터**가 토큰 뒤에 있어야 한다.

1. `issueTeacherToken(candidate)` — 검증 성공 시 랜덤 토큰을 발급하고 만료시각과 함께 `SIH_TCH_인증` 탭에 저장
2. `SIH_TCH_` 접두사 탭에 대한 모든 접근은 유효 토큰이 없으면 거부 (규칙 4)

이러면 `isUnlocked`를 강제로 켜도 **UI 껍데기만 열리고 데이터가 오지 않는다.** 실질적 방어가 성립한다.

**남는 취약점: 짧은 비밀번호에 대한 온라인 무차별 대입.**

`verifyPassword`가 공개 엔드포인트이므로 4자리 숫자 비밀번호는 최대 10,000회 시도로 뚫린다. GAS 응답 지연(1~3초)과 동시 실행 상한(30)이 자연적인 rate limit 역할을 하지만 설계된 방어가 아니다. 완화책:

- 기본 비밀번호를 4자리에서 **6자리 이상**으로 올리고 교사에게 변경을 유도
- shim이 실패 횟수를 `SIH_TCH_인증`에 기록하고 N회 초과 시 일정 시간 거부

**위협 모델을 명시할 필요가 있다.** 이 앱이 방어해야 할 대상은 국가급 공격자가 아니라 "동기가 있는 학생이 성적·평가를 조작하는 것"이다. 그 기준에서는 위 조합으로 충분하다. 성적 데이터의 법적 민감도가 올라가는 상황이 오면 11장의 B안(공용 서버 + OAuth)으로 넘어가는 것이 맞다.

## 9. 요약

- 현재 구조가 OAuth 없이 동작하는 이유는 **교사가 자기 계정으로 자기 스크립트를 직접 배포했기 때문**이다. 인증은 배포 시점에 1회 끝나 있다.
- Code.gs 642줄은 **로직 결합도 0, 스키마 결합도 100**이다. "코드는 통제된다"는 맞지만 "스키마 마이그레이션은 통제되지 않는다".
- 순진한 shim은 스키마 권한을 서버 1곳에서 브라우저 N개로 분산시켜 오히려 위험하다.
- **규칙 4개**(버전 핸드셰이크 / 탭 버저닝 / append-only / 접두사 권한)를 얹으면 shim이 스키마를 몰라도 현재보다 안전해진다. 규칙 1과 규칙 4는 반드시 최초 배포에 포함해야 한다.
- 검증 과정에서 **파괴적 연산 4곳**(그중 탭 전체 삭제 2곳, 빈 페이로드 가드 없음)이 발견되었다. shim 전환 여부와 별개로 검토가 필요하다.

## 11. 아키텍처 선택 가이드 — 구글 시트를 백엔드로 쓸 때

이 장은 이 프로젝트에 한정되지 않는다. 앞으로 새 프로젝트에서 구글 스프레드시트를 데이터 저장소로 쓸지, 쓴다면 어느 구조로 갈지 판단하기 위한 정리다.

### 11.0 먼저: 시트를 DB로 써도 되는가

아키텍처를 고르기 전에 이 질문이 먼저다. 아래 한계는 **구조와 무관하게** 공통으로 적용된다.

| 항목 | 실제 값 |
|---|---|
| API 쿼터 | 프로젝트당 분당 300 요청, 사용자당 분당 60 (읽기·쓰기 각각) |
| 셀 상한 | 스프레드시트당 1,000만 셀 |
| 응답 지연 | 200ms ~ 수 초 |
| 트랜잭션 | 없음 |
| JOIN·인덱스·검색 | 없음. 전체를 읽어 클라이언트에서 필터링 |
| 동시 쓰기 | `values.append`는 안전. 읽기→계산→쓰기 패턴은 레이스 발생 |

**적합한 경우**

- 행 수가 수만~수십만 이하
- 쓰기 빈도가 낮음 (초당 1건 미만)
- **사람이 데이터를 직접 열어보고 손으로 고쳐야 함** ← 시트를 고르는 가장 강력한 이유
- 별도 관리자 화면을 만들 예산·시간이 없음
- 데이터 소유자가 개발자가 아니라 사용자여야 함

**부적합한 경우**

- 실시간 반영, 초당 수십 건 이상 쓰기
- 전문 검색, 관계형 질의, 집계 쿼리
- 사용자 수가 수천 명 이상
- 금액·재고처럼 트랜잭션 정합성이 필요한 데이터

교육용 도구, 소규모 사내 도구, 설문·신청 수집처럼 "관리자가 엑셀로 보고 싶어하는" 데이터는 시트가 정답에 가깝다. 반대로 일반 웹 서비스의 사용자 DB로는 쓰면 안 된다.

### 11.1 세 가지 구조

| | **A. GAS 프록시** | **B. 공용 서버 + OAuth** | **C. 서비스 계정** |
|---|---|---|---|
| 대표 사례 | 이 프로젝트 | `FVG_project` | 일반적인 "시트 = DB" 패턴 |
| 데이터 소유자 | 각 사용자 | 각 사용자 | **개발자** |
| 최종 사용자 로그인 | 불필요 | 불필요 | 불필요 |
| 관리자 로그인 | 불필요 | 필요 (구글 OAuth) | 불필요 |
| 배포 단위 | 사용자 1명 = 배포 1개 | 공용 배포 1개 | 공용 배포 1개 |
| Google Cloud Console | **불필요** | 필수 (OAuth 클라이언트, 동의 화면, Picker 키) | 필수 (서비스 계정 + 키) |

### 11.2 A와 B의 상세 비교

| 항목 | A. GAS 프록시 | B. 공용 서버 + OAuth |
|---|---|---|
| 초기 구축 시간 | 짧음. 인증 코드가 0줄 | 김. OAuth 흐름·토큰 갱신·암호화 구현 필요 |
| 사용자 온보딩 | 사본 뜨기 + 배포 + 승인 (5~10분, 경고 화면) | 로그인 클릭 + 시트 선택 (30초) |
| 서버 로직 업데이트 | 각 사용자 재배포. **shim + 규칙 적용 시 사실상 불필요** | `git push` |
| 스키마 변경 | shim + 규칙 적용 시 `git push` | `git push` |
| 응답 지연 | 1~3초 (cold start 포함) | 200~500ms |
| **API 쿼터** | **사용자 계정별로 분산 — 사실상 확장 무제한** | 개발자 프로젝트 1개에 집중 (분당 300) |
| 개발·디버깅 | 나쁨. GAS 편집기, 배포마다 버전 관리 | 좋음. 로컬 개발, 일반 도구 체인 |
| 자격증명 위치 | 사용자의 스크립트 (개발자 접근 0) | 링크 안에 암호화 (서버 무저장) |
| 유출 시 피해 범위 | `/exec` URL = 그 시트 | 링크 = 그 시트 (동일) |
| 개발자의 데이터 책임 | 없음 | 없음 (무저장 설계 유지 시) |
| 운영 비용 | 0 | 0 (Vercel 등 무료 티어) |

**A가 유리한 조건**

- 사용자가 수십 명 규모이고 각자 자기 데이터를 소유해야 함
- 개발 기간이 짧고 인증 코드를 쓸 여유가 없음
- 사용자 수가 늘어도 쿼터 걱정이 없어야 함
- 사용자가 최초 1회 설정 절차를 감당할 수 있음 (사내 도구, 교사·담당자 대상)

**B가 유리한 조건**

- 온보딩 자체가 제품의 일부 (불특정 다수에게 배포)
- 업데이트가 잦고 전원이 같은 버전을 써야 함
- 응답 속도가 사용자 경험에 중요
- 서버 측 검증·권한 분리가 실제로 필요한 수준의 민감 데이터

**공통 주의**: B를 고를 때 스코프는 반드시 `drive.file`을 쓴다. `spreadsheets` 전체 스코프는 구글의 앱 검증 심사와 테스터 100명 상한을 유발한다. `drive.file`은 비민감 스코프로 분류되어 심사 없이 프로덕션 게시가 가능하고, 읽기·쓰기·시트 추가·서식 지정을 모두 지원한다.

### 11.3 C. 서비스 계정 — 가장 단순하지만 소유권이 바뀐다

**데이터를 개발자가 소유해도 되는 경우, A와 B 둘 다 필요 없다.**

절차:
1. Google Cloud에서 서비스 계정 생성, JSON 키 발급
2. 대상 스프레드시트를 서비스 계정 이메일에 **편집자로 공유**
3. 서버가 JWT로 access token을 받아 Sheets API 호출

OAuth 흐름이 없고, 사용자 로그인이 없고, Picker가 없고, 리다이렉트 URI 등록도 없다. 코드가 A·B보다 훨씬 적다.

**대가와 함정**

- **데이터가 개발자 관리 하에 들어간다.** 개인정보·미성년자 데이터를 다룬다면 개발자가 데이터 관리자가 되고 그에 따르는 책임이 생긴다. 이 프로젝트와 `FVG_project`가 C를 선택하지 않은 이유가 정확히 이것이다.
- **서비스 계정에는 Drive 저장 용량이 없다.** 서비스 계정 이름으로 스프레드시트를 **생성**하면 소유자 없는 파일이 되어 문제가 생긴다. 반드시 사람이 만든 파일을 공유받아 쓰거나, 생성 후 소유권을 이전해야 한다. 자주 걸리는 함정이다.
- 키 파일 유출 시 그 계정에 공유된 **모든 시트**가 한 번에 노출된다.
- 사용자별 데이터 분리가 자연스럽지 않다. 시트를 사용자마다 만들면 결국 매핑 저장소가 필요해진다.

**C가 맞는 경우**: 사내 도구, 설문·신청 수집, 개발자가 운영 주체인 대시보드. 즉 "시트는 그냥 내 DB인데 관리자가 엑셀로 보고 싶어함"인 상황.

### 11.4 결정 순서

```
1. 시트가 DB로 적합한가? (11.0)
   아니오 → 진짜 DB를 쓴다. 시트는 내보내기 용도로만.
   예 ↓

2. 데이터를 개발자가 소유해도 되는가?
   예 → C. 서비스 계정. 가장 단순하다.
   아니오(사용자가 소유해야 함) ↓

3. 사용자가 최초 1회 설정 절차(배포·승인)를 감당할 수 있는가?
   그리고 사용자 규모가 수십~수백인가?
   예 → A. GAS 프록시 + 이 문서의 규칙 4개
   아니오(불특정 다수 / 온보딩이 제품의 일부) ↓

   참고 구현체: FVG_project
```

### 11.5 A와 B 사이의 전환

A에서 B로 옮기는 것은 가능하지만 비용이 크다 — 인증 계층을 새로 만들고, 사용자 전원이 다시 온보딩해야 한다. 반대로 B에서 A로 가는 경우는 거의 없다(공용 배포를 포기하는 것이기 때문).

따라서 **초기 판단에서 "사용자 규모가 세 자릿수를 넘길 가능성"과 "온보딩 난이도를 사용자가 감당할 수 있는지" 두 가지를 먼저 정하는 것이 실질적으로 중요하다.** 나머지 항목은 대부분 나중에 조정할 수 있다.

전환 비용을 낮추려면 A로 시작하더라도 **스키마 지식을 클라이언트에 두는 구조**(이 문서의 shim 설계)를 유지하는 편이 낫다. B로 옮길 때 스키마 정의 모듈을 그대로 서버로 이동시키면 되기 때문이다.
